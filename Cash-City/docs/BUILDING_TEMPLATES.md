# Original storefront shell

`BuildingTemplates.storefront(config, optionalDoorComponent)` returns an unparented, original single-story Model. Nothing runs or inserts into the live city until the Lead explicitly imports and calls it. No branding or external art is used.

The default shell is32×28studs with14stud clear height, a6×9stud front entrance aperture, two glazed structural window openings, separated walls, floor and solid roof/ceiling. Coordinates use floor topY=0; storefront faces local negativeZ. The entry has no raised threshold. The room has a clear central path; there are no claimed stairs, elevators, upper stories or furnished interiors. Glass panes collide; they are static windows, not advertised as opening/breakable interactions. Window trim does not collide. Shell parts are anchored and touch events disabled.

Config accepts `width`24..80, `depth`16..80, `height`12..24, `wallThickness`.3..1, `doorWidth`5..8, `doorHeight`8..11, `material` as Enum.Material name, `color` as Color3 and `cframe` as CFrame. Only `stories=1` is supported. Invalid parameters fail before model creation. Window widths adapt to frontage while retaining piers. All units are studs. Defaults are estimates, not surveyed Detroit architecture.

Without a door component, `DoorIntegration="OpenApertureNoDoor"`; access is through the open aperture. This is a traversable shell, not a completed building feature.

An optional door component must be an Archivable Model using the existing InteractionRegistry contract: direct Moving Model, MotionPivot BasePart, Control BasePart containing ProximityPrompt, MotionHinge/Slide, AxisX/Y/Z and finite Travel attributes. The factory clones it, retains those properties, addsSSInteractable and places its Model pivot at the entrance aperture center. Author the component pivot accordingly and its panel to fit within the configured aperture; the factory does not resize components. The caller must separately run the central InteractionRegistry for the containing root after parenting. `ComponentProvidedAwaitingRegistry` is an integration status, not proof of working door motion. Motion clearance, actual open/close, collision, multiplayer permissions and input-device behavior require subsequent validation. No per-door scripts are created.

Lead validation: import the module as ServerScriptService.BuildingTemplates and run `tests/STUDIO_BUILDING_TEMPLATE_CHECK.lua` in Edit/Server. It uses temporary fixtures, checks three dimensions with rotated placement, tests actual doorway/corridor overlap queries, anchored geometry, static glazing, noncolliding trim and invalid parameters. Cleanup occurs on success and failure. Harness supplied; actual Studio execution must be recorded separately. A valid functional door fixture and multiplayer interaction test remain dependencies.
